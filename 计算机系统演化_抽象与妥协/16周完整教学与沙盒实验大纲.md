## 模块一：物理限制与数值表示（第 01 - 02 周）

### 第 01 周 | 导论：系统的第一性原理与定量工具

* **理论推演**
  * **上半场：抽象的代价与三大物理限制**
    * 抽象泄漏定律：软件的每一层抽象都是为了隐藏底层细节，但当性能逼近极限时，被隐藏的物理限制总会暴露出来。
    * 决定计算机设计的三大物理限制：**芯片面积（Die Area）**、**功耗与散热限制（数据搬运消耗的能量往往是算术运算本身的几十到上百倍）**、**光速延迟极限（电信号在芯片和光纤中每纳秒只能传播约 15\~20 厘米）**。
  * **下半场：贯穿全课的三个定量工具**
    * **Roofline 模型（屋顶线模型）**：横轴是算术强度 $I = \text{FLOPs}/\text{Byte}$（每读写 1 字节内存能做多少次浮点运算），纵轴是实际算力。带大家算出主流 GPU 的性能拐点，理解为什么大部分逐元素运算和大模型逐词生成都卡在内存带宽上。
    * **利特尔法则（Little's Law, $L = \lambda W$）**：要想跑满内存带宽 $\lambda$，同时掩盖长达几百个时钟周期的访存延迟 $W$，硬件必须同时维持多少个并发请求 $L$？
    * **阿姆达尔定律（Amdahl's Law）**：定量计算串行部分和跨节点通信时间是如何限制多卡集群扩展效率的。

### 第 02 周 | 数值表示：从 IEEE 754 到大模型分块量化

* **理论推演**
  * **上半场：IEEE 754 浮点数标准的设计取舍**
    * 符号位、指数位和尾数位是如何分配的？为什么浮点数在数轴上的分布越远离 0 就越稀疏？由此带来的“大数吃小数”现象，以及为什么浮点加法不满足结合律 $(a+b)+c \neq a+(b+c)$。
    * 次正规数（Subnormals）如何防止极小数值直接变成 0，以及为什么 GPU 通常默认把极小值直接截断为 0（Flush-to-Zero）以换取速度。
  * **下半场：跨代对照——从 FP32 到 BF16 / FP8 / INT4 分块量化**
    * 硬件乘法器的芯片面积与尾数位宽的平方成正比。把位宽从 32 位降到 8 位或 4 位，不仅让显存占用和带宽需求减少到原来的 $1/4 \sim 1/8$，同样大小的芯片面积还能塞进成倍的计算单元。
    * **BF16 与 FP8 (E4M3 / E5M2) 的分工**：为什么深度学习宁可牺牲尾数精度，也要优先保留足够的指数位宽来维持数值范围？
    * **离群值（Outliers）与分块缩放量化（Block-wise Scaling）**：当神经网络某几个通道出现远大于平均值的极端数值时，整张矩阵共用一个缩放比例为什么会导致其他正常数值全部丢失精度？如何通过“每 32 个数共用一个缩放因子”配合随机舍入（Stochastic Rounding）解决这一问题？

* **沙盒实验 1：精度与芯片面积的权衡**
  * **实验任务**：在给定芯片面积预算的模拟器中，编写分块量化算子（包含离群值分离、块级缩放系数计算与随机舍入逻辑），跑通一个 6 层 Transformer 模型的前向推理与反向梯度累加。
  * **评分标准**：

## 模块二：执行模式——CPU 乱序流水线 vs. GPU 大规模并行（第 03 - 04 周）

### 第 03 周 | 执行模式：追求低延迟的 CPU vs. 追求高吞吐的 GPU

* **理论推演**
  * **上半场：CPU 如何让单线程跑得更快——深流水线、分支预测与乱序执行**
    * 现代 CPU 为了降低单条指令流的执行延迟，把大半芯片面积花在了大容量多级缓存、复杂的分支预测器、寄存器重命名和乱序执行引擎上。
    * 当遇到 `if-else` 条件跳转时，CPU 先猜测一个方向往下跑；一旦猜错，就必须清空流水线重来（冲刷惩罚）。
  * **下半场：GPU 如何实现高吞吐——SIMT 锁步执行与分支分化问题**
    * 如果把 CPU 里占地方的分支预测器和乱序控制电路全部去掉，省下来的面积全部换成上万个简单的计算单元（ALU），就得到了 GPU。
    * **SIMT（单指令多线程）机制**：GPU 把 32 个线程编成一个**线程束（Warp）**，共用一套取指和译码电路，32 个线程在同一时刻执行完全相同的指令。
    * **GPU 的性能杀手——分支分化（Warp Divergence）**：如果同一个线程束里的 32 个线程遇到了 `if-else`，一部分线程满足条件走 `if`，另一部分走 `else`，硬件只能先让走 `if` 的线程执行（其余线程干等），然后再让走 `else` 的线程执行——实际执行时间直接翻倍，算力利用率减半。

### 第 04 周 | 跨代对照：从硬件投机执行到大模型投机采样

* **理论推演**
  * **上半场：硬件投机执行的副作用——幽灵（Spectre）侧信道漏洞**
    * 当 CPU 分支预测猜错时，虽然寄存器的值可以回滚恢复，但投机执行期间读入缓存（Cache）的数据却留在了硬件里。攻击者如何通过测量缓存访问快慢，把本无权访问的内存机密偷出来？
  * **下半场：跨代对照——大模型推理的投机采样（Speculative Decoding）**
    * 为什么大模型一个词一个词往外蹦（Decode 阶段）那么慢？因为每生成 1 个词，都要把几十 GB 的模型权重从显存搬运到计算单元一次，绝大部分时间都在等显存读取，GPU 的并行计算单元根本吃不饱。
    * **跨代设计对照**：
      * CPU 分支预测器 $\longleftrightarrow$ 用参数量很小、速度极快的草稿模型（Draft Model）先一口气连猜几个候选词；
      * GPU 并行计算优势 $\longleftrightarrow$ 大模型只需要**加载一次权重**，就能把这几个候选词放在一起同时验证完；
      * 分支猜错回滚 $\longleftrightarrow$ 通过拒绝采样算法截断猜错的部分并重新采样，在数学上保证最终生成的文本分布与大模型单独逐词生成**完全一致**。

* **沙盒实验 2：消除 GPU 分支分化与实现投机解码**
  * **实验任务**：
    * **上半场**：在 GPU 线程束模拟器中，改写一段存在严重 `if-else` 分支分化的核函数（利用无分支条件赋值和线程束内寄存器交换指令 `Warp Shuffle` 消除等待）。
    * **下半场**：编写树状投机解码的候选词树生成逻辑、构造防止不同分支互相干扰的注意力掩码（Attention Mask），并实现拒绝采样验证函数。
  * **评分标准**：
    * **及格线 (60%)**：上半场将线程束有效执行率从 $30\%$ 提升至 $90\%$ 以上；下半场投机解码的输出结果分布与原始模型完全吻合。
    * **优秀线 (85%)**：面对代码生成（容易猜准）和创意写作（不容易猜准）混合的请求流，编写动态调整猜测步长的控制逻辑，使整体生成速度提升 $2.4$ 倍以上。
    * **极客榜 (100%)**：综合平衡“多猜候选词增加的计算量”与“减少显存读取省下的时间”，跑出最高的单卡每秒生成词数（Token/s）。
* **阶段作业 1（占总评 7.5%）**：**故障与安全分析报告——《从 CPU 幽灵漏洞到大模型共享前缀缓存（Prefix Cache）的时间侧信道：为什么跨用户的缓存复用与投机执行容易导致隐私泄露？》**

## 模块四：时间调度——切换开销 vs. 零开销延迟掩盖（第 07 - 08 周）

### 第 07 周 | 时间调度：CPU 抢占切换开销 vs. GPU 零开销延迟掩盖

* **理论推演**
  * **上半场：为什么 CPU 切换线程的代价很高？**
    * CPU 的通用寄存器很少（如 x86 只有 16 个），每次切换进程或线程，不仅要把寄存器保存到内存、切换页表、刷新快表（TLB），更严重的是新线程会把原有线程留在缓存（L1/L2 Cache）里的热数据全部挤掉。
  * **下半场：GPU 是怎么靠“零开销切换”掩盖显存延迟的？**
    * 当 GPU 的一个线程束发起显存读取、需要等待 400 个时钟周期时，它靠什么办法不让计算单元闲着？（**靠瞬间切换到别的就绪线程束继续计算！**）
    * 为什么 GPU 切换线程束不需要保存和恢复寄存器？因为 GPU 每个核心（SM）都配有一个极庞大的寄存器堆（例如 65,536 个寄存器），几十个线程束各自使用的寄存器是**提前划分好、同时常驻在芯片上**的。硬件切换到另一个线程束只需要改一下指针，**耗时为 0 个额外周期**！
    * **核心权衡：单线程寄存器用量 vs. 并发驻留率（Occupancy）**：如果每个线程为了做复杂计算占用了太多寄存器，芯片上能同时常驻的线程束数量（Occupancy）就会大幅减少，不够用来掩盖显存延迟；反过来，如果强行限制寄存器数量，超出的数据就会溢出到慢速显存（Register Spilling），直接拖垮内存带宽。

### 第 08 周 | 跨代对照：从异步事件循环到 Continuous Batching

* **理论推演**
  * **上半场：排队延迟曲线与异步 I/O (`epoll` / `io_uring`)**
    * 排队论基本规律：当硬件利用率逼近 $100\%$ 时，新请求的排队等待时间会呈指数级飙升。操作系统如何通过事件循环（`epoll`）和无锁环形队列（`io_uring`）避免线程阻塞与频繁切换？
  * **下半场：跨代对照——大模型推理的连续批处理与分块预填充**
    * 静态批处理（Static Batching）的问题：同一批请求里，短回答早就生成完了，却必须陪着长回答一起干等。
    * **连续批处理（Continuous Batching）**：把调度粒度细化到“每生成一个词（单步迭代）”——只要批里有一个请求生成结束，立刻在下一步把新请求补进空位。
    * **预填充（Prefill，计算密集）与逐词解码（Decode，访存密集）的冲突**：一个上万字的长文档预填充插进来，会独自占满 GPU 几百毫秒，导致同批次正在逐字输出的几十个用户画面突然卡顿。如何通过 **分块预填充（Chunked Prefill，把长输入切成小段，夹在解码步骤中顺带算完）** 或 **预填充与解码分机部署（P/D 分离）** 解决卡顿？

* **沙盒实验 4：编写高吞吐低延迟的推理调度器**
  * **实验任务**：实现推理引擎的核心单步调度函数（`Scheduler.step()`），包含动态插拔请求槽位、分块预填充（Chunked Prefill）配额控制，以及当显存不足时的无死锁换出（Swap）与重算（Recompute）策略。
  * **评分标准**：
    * **及格线 (60%)**：在突发流量下不发生显存死锁，且长请求不会一直排不上队（无饥饿现象）。
    * **优秀线 (85%)**：同时满足两项延迟要求——**首字返回延迟（TTFT P95）$< 450\text{ms}$**，**逐字输出间隔（TPOT P99）$< 35\text{ms}$**，且 GPU 平均算力利用率达到 $78\%$ 以上。
    * **极客榜 (100%)**：根据实时排队情况动态调节每一步混入的预填充词数，在长短请求混合的测试流下跑出最高的达标吞吐量（Goodput）。
* **阶段作业 2（占总评 7.5%）**：**定量计算报告——《给定 GPU 核心的寄存器总数、片上缓存容量与显存延迟，定量推导一个核函数在“增大单线程分块尺寸”与“保持足够并发线程束数量（Occupancy）”之间的最佳平衡点》**

### 第 10 周 | 跨代对照：大模型多卡并行策略与 RDMA 零拷贝网络

* **理论推演**
  * **上半场：当单张显卡装不下模型——三种并行策略的通信账本**
    * 对比三种切分方式各自的**通信数据量、同步频率与网络要求**：
      1. **数据并行与零冗余优化器（DP & ZeRO）**：每张卡跑不同数据，把模型参数、梯度和优化器状态分摊到各张卡上，用时再临时收集，可以通过“边算边传”把通信时间藏在计算时间背后；
      2. **张量并行（Tensor Parallelism, TP）**：把同一层里的矩阵乘法切开分给多张卡同时算。代价是**每算完一层都必须立刻做一次全卡同步（AllReduce）**，对延迟极其敏感，通常只能用在服务器内部具备超高速互联（NVLink）的显卡之间；
      3. **流水线并行（Pipeline Parallelism, PP）**：按网络层数切分到不同机器。通信数据量很小（只传层间结果），但容易在启动和收尾阶段产生大量等待空闲（流水线气泡 Bubble）。
  * **下半场：为什么高速网络必须绕过操作系统内核——GPUDirect RDMA**
    * 在 400G/800G 高速网络下，如果还按传统方式让网卡中断 CPU、把数据拷进操作系统内核缓冲区、再拷进显卡显存，光内存拷贝就能把 CPU 占满，导致显卡长时间干等。
    * **RDMA 内核旁路与零拷贝**：让网卡直接跨过 CPU 和操作系统，通过 PCIe 直接读写远端服务器的 GPU 显存；以及环形同步（Ring-AllReduce，省带宽）与树形同步（Tree-AllReduce，降延迟）的适用场景。

* **沙盒实验 5：多卡并行切分与计算通信重叠**
  * **实验任务**：在 64 卡跨机架集群模拟器（机内 8 卡高速互联，机间普通高速网）中，配置数据并行、张量并行与流水线并行的组合比例，编写 1F1B（一前一后）微批次流水线调度，并实现反向传播计算与梯度通信的异步重叠。
  * **评分标准**：
    * **及格线 (60%)**：单卡峰值显存占用不超过硬件上限，流水线执行无死锁。
    * **优秀线 (85%)**：将流水线空闲气泡比例压到 $12\%$ 以下，将通信未被计算掩盖的等待时间压到 $8\%$ 以下，集群整体有效算力利用率（MFU）达到 $52\%$ 以上。
    * **极客榜 (100%)**：结合机内与机间分层通信（Hierarchical AllReduce）与交错式流水线调度，在存在个别慢节点抖动的情况下冲击 $62\%$ 以上的集群算力利用率。

## 模块六：编程抽象——片上缓存分块与块级编译（第 11 - 12 周）

### 第 11 周 | 编程抽象：为什么传统 C 语言难以直接发挥现代硬件性能？

* **理论推演**
  * **上半场：C 语言的平坦内存假设与现代硬件的脱节**
    * C 语言诞生于单核、顺序执行、没有多级缓存的年代。面对现代多核向量指令（SIMD）和 GPU 架构，C 语言里的任意指针引用（编译器无法确定两个指针是否指向同一块内存）和一维单步循环，反而让编译器很难自动做好并行化与缓存复用。
  * **下半场：矩阵乘法的性能关键——片上缓存分块（Tiling）**
    * 算一笔显存读写账：两个 $N \times N$ 矩阵相乘，总共需要做 $2N^3$ 次乘加运算。
    * 如果按最普通的三重循环来写，每算一次都要去慢速显存里读数据，算力利用率连 $2\%$ 都不到。
    * **分块计算（Tiling）**：把大矩阵切成能装进芯片内部高速缓存（SRAM / Shared Memory）的小方块（如 $128 \times 128$），从显存读一次进片上缓存，在片上反复使用上百次后再写回结果，显存读写量直接减少上百倍，算力利用率随之大幅跃升。
    * **片上缓存的存储体冲突（Bank Conflict）**：为什么片上缓存被分成了 32 个独立的存储体（Bank）？为什么按列跨步读取会导致 32 个线程撞在同一个存储体上排队？如何通过错位存放（Padding 或地址异或交错）消除排队？

### 第 12 周 | 跨代对照：FlashAttention 在线计算与 Triton 块级编程

* **理论推演**
  * **上半场：FlashAttention 是怎么省掉巨型中间矩阵的？**
    * 标准注意力公式 $\text{Softmax}(QK^T)V$ 的瓶颈：中间结果 $QK^T$ 是一个 $N \times N$ 的大矩阵。当输入长度 $N=32\text{K}$ 时，光把这个中间矩阵写回显存再读出来算 Softmax，显存带宽就被占满了。
    * **在线分块计算（Online Softmax）**：不需要等整行算完才求最大值，而是边按小块读取、边在片上缓存里动态修正缩放比例，一口气在片上算完最终结果——**全程根本不把 $N \times N$ 的中间矩阵写回显存**。
  * **下半场：从繁琐的 CUDA 线程管理到 Triton 的块级编程**
    * 为什么直接写底层 CUDA 代码门槛极高？（程序员必须手动计算每个线程的坐标、手动管理片上缓存同步和双缓冲）。
    * **Triton 的设计思路**：让程序员只用关心最影响性能的核心问题——**“数据块（Tile）切多大、怎么在显存和片上缓存之间流转”**，而把枯燥的单个线程分配和底层指令生成交给编译器自动完成。

* **沙盒实验 6：手写分块矩阵乘法与 FlashAttention 核函数**
  * **实验任务**：在类 Triton 的块级编程沙盒中，编写：
    1. 带双缓冲异步预取（一边算当前数据块，一边提前把下一块读入缓存）的分块矩阵乘法；
    2. 基于在线 Softmax 递推公式的 FlashAttention 前向计算核函数。
  * **评分标准**：
    * **及格线 (60%)**：计算结果与标准实现误差小于 $10^{-3}$，且单块片上缓存占用不超标。
    * **优秀线 (85%)**：将注意力计算的显存总读写量减少 $85\%$ 以上，实际运行速度达到硬件理论上限的 $82\%$ 以上。
    * **极客榜 (100%)**：消除片上缓存的存储体冲突（Bank Conflict），并针对因果掩码（Causal Mask）直接跳过无需计算的上三角空白块，冲击 $92\%$ 以上的硬件算力利用率。
* **阶段作业 3（占总评 7.5%）**：**技术演进分析——《对比传统 CUDA 线程级编程与 Triton 块级编程：软件抽象是如何随着 GPU 矩阵计算单元和异步数据搬运硬件的演进而不断调整边界的？》**

### 第 14 周 | 前沿探讨：把大模型看作“概率处理器”与确定性护栏设计

* **理论推演**
  * **上半场：概率处理器的特性与多步任务的错误累积**
    * 把大模型看作一颗以自然语言为指令、以上下文窗口为寄存器的“概率处理器”。

  * **下半场：用确定性代码框住概率模型——现代 Agent Harness 架构**
    * 利用**“生成难、验证易”**的不对称性：让大模型负责发散猜方案，让确定性的程序（编译器类型检查、语法状态机、单元测试沙箱）负责严格把关。
    * **状态机约束解码（FSM / CFG Guided Decoding）**：在模型每生成一个词之前，用正则表达式或 JSON 语法状态机直接把不符合语法规则的词的概率置为 0，保证输出的格式 **100% 合法**。
    * **按需多路搜索**：监测模型输出时的不确定度（信息熵）——模型非常笃定时直接单路往下走；模型犹豫不决时自动分出多条分支并行尝试，并用测试沙箱选出能跑通的一条。

* **沙盒实验 7：实现状态机约束解码与自适应重试闭环**
  * **实验任务**：针对一个需要连续调用外部工具并输出复杂结构化数据的模型接口，编写：
    1. 基于语法状态机的实时词表掩码器（Logits Mask），强制输出合法的 JSON 与工具调用格式；
    2. 根据输出信息熵动态触发分支采样、并结合沙箱执行反馈自动修正错误的控制循环。
  * **评分标准**：
    * **及格线 (60%)**：将原本成功率不足 $25\%$ 的 10 步复合任务提升至 $95\%$ 以上，格式解析错误率为 $0\%$。
    * **优秀线 (85%)**：结合前缀显存复用与信息熵阈值控制，在保持 $98\%$ 成功率的同时，把平均消耗的 Token 数量控制在无脑多路采样方案的 $25\%$ 以内。
    * **极客榜 (100%)**：在工具接口随机报错与返回异常数据的干扰测试下，取得最高的“成功率 / 计算耗时”综合得分。
